# POS Colombia

Punto de venta minorista API-first para una tienda de barrio. Idioma de UI y copy: español (Colombia).

## Stack y comandos

- `apps/api`: FastAPI + SQLAlchemy + Alembic + PostgreSQL 16. `apps/web`: Next.js 16 + React 19 + TypeScript + Tailwind 4.
- Ejecutar todo: `docker compose up --build` (web :3000, API :8000/docs). Tras cambiar código: `docker compose up -d --build api web`.
- Tests backend: `cd apps/api; $env:PYTHONPATH="."; pytest`. Frontend: `cd apps/web; npm run typecheck; npm run build`.
- Casi todos los tests corren sobre SQLite en memoria; las pruebas que necesitan locks reales se hacen contra una copia de Postgres (nunca contra la base real).

## Reglas de negocio que un cambio visual NUNCA modifica

- El inventario es un ledger: stock = suma de `inventory_movements`. Nunca se escribe `product.stock`.
- Operar (vender, recibir compra, ajustar, contar) exige jornada abierta (`CashSession`, guard `require_open_session`).
- `Sale OPEN` y `Purchase DRAFT` viven en el backend. La UI solo las muestra y edita mediante los contratos existentes. Una venta OPEN descartada se marca CANCELLED (nunca se borra); solo las ventas COMPLETED cuentan en reportes y caja.
- Conteo físico: preview sin escritura, confirmación por lote (`reference_id`), `expected_current_stock` (409 si cambió), un error bloquea todo el lote.
- Códigos UPC-A/EAN-13 se resuelven con `app/services/barcodes.py`; nunca se modifica `Product.barcode`.
- El rediseño consume los contratos API actuales. Si un cambio visual exige cambiar un contrato, se propone aparte y se aprueba antes.

### 1. Filosofía
- Es una interfaz operacional de caja, no un dashboard SaaS: rápida, táctil, legible, predecible, pocos toques.
- Conserva el modelo mental de los POS tradicionales (módulos grandes, tabla de venta, teclado numérico visible, inventario en tabla densa) con estética moderna. No clonar ningún software existente.
- La estética nunca cuesta velocidad. Ante duda entre bonito y rápido, gana rápido.
- Concepto visual "Mostrador": la caja registradora y la tienda de barrio como vocabulario. El elemento memorable es la **tecla física** (teclas con relieve y estado de pulsado). Todo lo demás es sobrio.
  - **Tecla**: botón con borde inferior grueso que "se hunde" al pulsar.
  - **Toldo**: banda superior con rayas propias de cada módulo. Identifica el contexto sin depender del color.
  - **Display**: panel oscuro tipo visor de caja para TOTAL, cambio y sumas.

### 2. Objetivo de hardware y breakpoints
- Objetivo principal: SUNMI T1 mini / T1mini-G, 1366×768 táctil. Alto útil real ≈ 1366×680 (barra del sistema/navegador): diseñar para ese alto, con la app en pantalla completa (PWA/kiosco).
- Se diseña primero para 1366×768 y luego se reorganiza. El responsive cambia la estructura, no solo los tamaños. Usa estos puntos de quiebre (definidos en Tailwind `@theme`):

| Rango | Nombre | Venta | Tablas |
|---|---|---|---|
| ≥1200 | `pos` | tabla + columna de cobro fija (~400 px) con teclado numérico | densas, todas las columnas |
| 900–1199 | `laptop` | tabla + columna de cobro (~340 px), teclado compacto | se ocultan columnas secundarias |
| 640–899 | `tablet-v` | una columna; barra inferior fija con TOTAL y COBRAR; teclado en hoja inferior | filas en dos líneas |
| <640 | `movil` | una columna; contextos en selector; COBRAR fijo abajo | filas apiladas (no rejilla de cards) |

- Prohibido: anchos fijos en px que rompan <1200, scroll horizontal de página, contenido crítico bajo el pliegue de 680 px de alto en Venta.
- Preferir `@container` para componentes que viven en columnas de ancho variable.

### 3. Touch-first (obligatorio)
- Objetivo táctil mínimo 48×48 px con 8 px de separación. Acciones frecuentes 56 px. Teclas del teclado numérico 64 px. COBRAR ≥ 88 px de alto.
- Nada depende de hover: `:hover` solo como mejora dentro de `@media (hover: hover)`. Toda acción tiene estado `:active` visible (≤ 80 ms).
- Acciones críticas (COBRAR, Recibir, Confirmar) siempre visibles sin scroll.
- Campos numéricos con `NumberPad` propio en Venta y Compra. El campo del escáner usa `inputMode="none"` y un botón para abrir el teclado bajo demanda: no debe abrir el teclado del sistema con cada enfoque.
- Modales y hojas: no se cierran al tocar el fondo si hay datos sin guardar; sin `window.confirm`/`alert` (usar `ConfirmDialog`). Botones de acción en la zona inferior.
- Scroll: un solo contenedor con scroll por zona, `overscroll-behavior: contain`, tablas con encabezado fijo.

### 5. Tipografía
- Titulares, cifras grandes y TOTAL: **Bricolage Grotesque** (variable). Cuerpo, tablas y formularios: **Atkinson Hyperlegible Next** (variable). Ambas locales con `@fontsource-variable/*`, subset latin, sin CDN. Verificado: ambas soportan la característica `tnum`, pero sus dígitos por defecto son proporcionales. Toda cifra de dinero, cantidad o TOTAL debe llevar `font-variant-numeric: tabular-nums` (clase `ui-num`). Bricolage NO se usa en tablas densas (ahí va Atkinson).
- Escala fluida con `clamp()` en px (tokens `--text-*`): micro 14 (mínimo absoluto), cuerpo 18, tabla 18, subtítulo 19–22, título 22–28, cifra clave 28–40, TOTAL 40–64. Las escalas grandes nunca son fijas.
- Prohibido texto de <14 px. Sentence case en etiquetas y encabezados; MAYÚSCULAS solo en TOTAL y en el CTA COBRAR. Sin "etiquetas eyebrow" en mayúsculas sobre cada título, sin cadenas "A · B · C" como decoración, sin "→" añadido a botones.
- Cifras de dinero: siempre `lib/format.ts` (`money`), `es-CO`, COP sin decimales, alineadas a la derecha con cifras tabulares.

### 6. Tokens de forma, espacio y movimiento
- Tamaños táctiles: `--size-touch` 48, `--size-touch-lg` 56, `--size-key` 64, `--size-cta` 88.
- Espacio (múltiplos de 4): `--sp-1` 4, `--sp-2` 8, `--sp-3` 12, `--sp-4` 16, `--sp-6` 24, `--sp-8` 32. Gutter de pantalla `--gutter`: 16 (móvil) / 24 (≥900).
- Radios con jerarquía (no un solo radio): `--radius-key` 10 (teclas y botones), `--radius-panel` 14 (paneles), `--radius-chip` 999, `--radius-input` 8.
- Sombras: solo dos. `--shadow-key`: `0 4px 0 <deep del módulo>` (relieve de tecla). `--shadow-panel`: `0 1px 2px rgb(0 0 0 / .08)`. Prohibido `blur` grande, `backdrop-filter` y sombras animadas (rendimiento en SUNMI). Los degradados solo se admiten como patrón estático del toldo (`ui-toldo`).
- Breakpoints Tailwind (min-width): `tablet:` 640, `laptop:` 900, `pos:` 1200 (móvil = sin prefijo). Para cambiar comportamiento (no layout) usa `useBreakpoint()`.
- Movimiento (microinteracciones, sin espectáculo): `--t-press` 80 ms, `--t-state` 150 ms, `--t-panel` 200 ms, curva `--ease`. Solo animar `transform` y `opacity`. Permitido: feedback de pulsado, cambio de pestaña, entrada suave de tarjetas (una sola vez), loaders, confirmación de éxito. Prohibido: animaciones >250 ms en flujos de caja, elementos que flotan, rebotes, entradas escalonadas por sección. Respetar `prefers-reduced-motion` (reducir a cambio instantáneo).
- Foco: `:focus-visible` con anillo de 3 px (`--focus` = `deep` del módulo o `#1D4ED8`) en todo elemento interactivo.

Cada módulo se reconoce por **cuatro señales a la vez**: color, icono, título de contexto y patrón de toldo. Nunca solo color.

| Módulo | Título de contexto | Patrón del toldo |
|---|---|---|
| Ventas | "Venta 1", "Venta 2" | rayas verticales anchas |
| Compras/Recepción | "Recepción · Proveedor" | rayas diagonales |
| Inventario | "Inventario" | puntos |
| Proveedores | "Proveedores" | zigzag |
| Caja | "Caja" | doble línea |
| Informes | "Informes" | líneas finas horizontales |

- Toda pantalla de módulo empieza con `PageHeader`: toldo + icono + título de contexto (+ acciones). Una sola cabecera por pantalla.
- La navegación no se duplica: el Home lista los módulos; la barra superior solo muestra Inicio, los contextos abiertos y la jornada.

### 8. Contextos simultáneos (Venta y Compra) — implementado en Fase 3
- Venta y Compra no se bloquean entre sí: cada una vive en su propia ruta (`/sales`, `/purchases`) con estado real en el backend (`Sale OPEN`, `Purchase DRAFT` con autoguardado), nunca se pierde al cambiar de módulo.
- `lib/workContexts.ts` (store con `useSyncExternalStore`) + `components/ContextBar.tsx` (montada en `layout.tsx` junto a `AppHeader`) son la barra global de contextos: `[Venta 1] [Venta 2] [Compra · Proveedor]`, clicable desde cualquier pantalla.
- Se oculta con menos de 2 contextos en total (una sola venta normal no necesita barra) y, para no triplicar información, cada pantalla oculta ahí los contextos que ya muestra por sí misma: en `/sales` solo aparece el chip de Compra (las tabs de venta ya están ahí); en `/purchases` solo aparecen los chips de Venta.
- Un clic en un chip de venta activa esa pestaña sin recargar si ya se está en `/sales` (`requestActivateSale`/`onActivateSale`); un clic en el chip de Compra navega a `/purchases`, que rehidrata el mismo DRAFT desde `sessionStorage`.
- Solo se sostiene UNA compra "activa" a la vez (no hay tabs de compras, a diferencia de Venta): otras DRAFT existentes se resumen desde el historial de `/purchases`, no desde la barra global.
- `--chrome-h` (`app/shell.css`) = altura de `AppHeader` + `ContextBar` cuando esta última está visible (clase `has-context-bar` en `body`); las pantallas de altura fija (`.sale`, y por herencia `.purchase`) usan `--chrome-h`, nunca `--appbar-h` solo.

### 9. Tabla o tarjetas
- **Tabla densa (siempre)**: líneas de Venta, Inventario/productos, líneas de Compra, conteo físico y sus previews, importaciones, movimientos, lista de compras y de proveedores. Filas de 44 px (solo lectura) o 56–64 px (interactivas). Con miles de filas: virtualización o paginación en servidor, nunca todo el DOM. Buscador grande + escáner, encabezado fijo.
- **Tarjetas (permitidas)**: Home, resumen de Caja, bloques de Resumen operativo, Informes con gráficos, canales de pago, detalle de proveedor.
- Una tarjeta debe tener utilidad operacional (acción, estado o dato que se decide con él). No usar KPIs decorativos.

"+12% vs período anterior" en el "Rango" de Informes — nunca una segunda cifra). Pendientes, se crean cuando tengan uso real: `PageHeader`, `EmptyState`, `ActionPanel`.
Dos defectos de las primitivas compartidas, encontrados y corregidos en Fase 4 (afectaban a cualquier pantalla, no solo Inventario): `.ui-search__input` (SearchBar) mostraba el icono nativo de borrar de `type="search"` DUPLICADO junto al botón propio — se suprime con `::-webkit-search-cancel-button { display:none }`. `.purchase__head-title h1` y `.purchase-metric--accent b` tenían `color: var(--color-compras-deep)` fijo en vez de `var(--mod-deep, var(--color-compras-deep))`: cualquier pantalla que reutilizara esas clases fuera de Compras (como Inventario) heredaba el título/acento en ámbar. Ojo con reutilizar una clase de otro módulo: si define un color, debe usar `--mod-deep`/`--mod-tint`, nunca el token del módulo original. Tercer defecto: `DataTable`'s `stack` (`.ui-table--stack .ui-td { display:flex }`) empataba en especificidad con `.sale-cart .ui-td { display:block }` de Venta, y por orden de `@import` en `globals.css` (`sales.css` después de `ui.css`) Venta ganaba — la fila apilada de Inventario se rompía en cuanto se le puso la clase `sale-cart`. Se corrigió subiendo la especificidad de la regla genérica (`table.ui-table--stack .ui-td`), pero la lección real es la de arriba: no reutilizar `sale-cart` fuera de Venta.

Cuarto defecto (Fase 5, la misma familia que el de `--chrome-h` en la sección 8): `--mod-deep`/`--mod-tint` se heredan por el árbol del DOM, no solo se leen donde se ponen. `<MetricCard label="Apertura" .../>` sin `module` seguía saliendo en rojo de Caja porque heredaba `--mod-deep` de `<main data-module="caja">`; el `var(--mod-deep, ...)` de `MetricCard` nunca cae al *fallback* porque la variable SÍ está definida (heredada), solo que con el valor equivocado para esa tarjeta puntual. La solución no es quitar `module`, es **redeclarar** la variable en el punto exacto donde se necesita el valor neutro (`.cash-metric--neutral { --mod-deep: var(--color-ink); --mod-tint: var(--color-paper); }`). Antes de asumir que omitir `data-module` aísla un elemento de la identidad del módulo, revisa si algún ancestro ya la puso — si sí, hay que redeclarar, no omitir.

Auditoría sistemática de `--mod-*` (Fase 6, sección 3 del encargo): se revisaron los 9 componentes compartidos más señalados (`MetricCard`, `Display`, `DataTable`, `InlineMessage`, `StatusBadge`, `TouchButton`, `Sheet`, `ConfirmDialog`, `SearchBar`). `Display`/`InlineMessage`/`StatusBadge` no usan `--mod-*` en absoluto (correcto: un mensaje de error o un estado nunca debe teñirse del color del módulo). Los otros seis sí lo usan a propósito (identidad/selección), y se confirmó por grep que **todo** `<Sheet>`, `<ConfirmDialog>` y `<SearchBar>` del proyecto pasa `module` explícito — cero casos de herencia accidental fuera del ya conocido de `MetricCard`. Además de la tarjeta de Caja, se encontró la misma trampa en los totales de Resumen (`.operations-groups__total-item`/`.operations-groups__grand-total`: Efectivo/Electrónico/Total vendido en rojo) y se corrigió igual (color directo a `--color-ink`, no `--mod-deep`). Regla operativa: **color del módulo = identidad, nunca "todo número en rojo es una alerta"** — una cifra financiera normal usa `ink`; el rojo/`--color-danger` se reserva para salidas de dinero o estados realmente semánticos.
Venta (`app/sales/`): `page.tsx` orquesta; `_components/` = `ScanBar` (consulta y resultados locales), `CartTable` (memoizada), `PaymentPanel` (dock ≥900 o dentro de `Sheet` en tablet/móvil), `SplitPaymentSheet`, y `ManualItemSheet` ("Producto manual", ver sección abajo; reemplazó a `ManualSaleModal`)/`ElectronicInvoicePanel` (restyled al design system en Fase 2.1, misma lógica y contratos). Reglas de la pantalla: alto = viewport − chrome (`100dvh − var(--chrome-h)`, ver sección 8), solo scrollea la tabla; escáner siempre enfocado (`refocus`); un código de 8–14 dígitos va directo a `POST /sales/{id}/items` (una sola ida y vuelta, el backend resuelve UPC↔EAN); cantidad y quitar son optimistas y se serializan en una cola; COBRAR y TOTAL siempre visibles; "Consumidor final" es solo una etiqueta (no hay cliente ni descuentos en el backend). "Cancelar venta" (`POST /sales/{id}/cancel`, Fase 2.1) cierra una OPEN sin cobrar: status CANCELLED con `cancelled_at`/`cancelled_by`, las líneas se conservan y no se crea ningún movimiento de inventario, pago ni movimiento de caja (idempotente; una venta COMPLETED no se puede cancelar). "Vaciar venta" se eliminó de la UI (cancelar cubre ese caso, con trazabilidad; ver por qué en el historial de la Fase 3). Al volver a `/sales` se restauran por `sessionStorage` la pestaña activa, el canal, el recibido y la última venta facturable de cada venta; se pierden (por diseño) el texto de búsqueda, los avisos y los modales.

Compras (`app/purchases/`, ámbar/`PackageOpen`) y Proveedores (`app/suppliers/`, morado/`Handshake`) — Fase 3. ### 11. Iconos e ilustraciones
- Iconos: `lucide-react` (SVG local, tamaño 24 por defecto, 32 en módulos, trazo 2). Prohibido usar caracteres como iconos (`×`, `＋`, `✓`, `⌕`).
- Ilustraciones: SVG propio y local, sin URLs externas, ≤ 6 KB cada una, en color con los acentos del módulo.
  - Sí: Home, estados vacíos, ayuda/onboarding. Mínimas en Venta e Inventario.
  - Estructura: `apps/web/components/illustrations/*.tsx` (SVG inline reutilizable) y `apps/web/public/illustrations/{home,empty,help}/*.svg` para las que no necesiten color dinámico.
  - Decorativas: `aria-hidden="true"`. Informativas: `role="img"` con texto alternativo.

### 12. Accesibilidad
- Contraste ≥ 4,5:1 para texto y ≥ 3:1 para bordes de controles y objetos gráficos. El estado nunca se comunica solo con color: añade icono y texto.
- Todo `input` con `<label>` visible o `aria-label`. Errores con `role="alert"`. Orden de tabulación lógico y atajos de teclado en Venta (Enter agrega, Esc cierra hojas).

### 13. Rendimiento en SUNMI
- Sin `backdrop-filter`, sin sombras con blur grande, sin degradados grandes ni imágenes pesadas. Fuentes: máximo 2 archivos variables `woff2` (latin). Listas largas virtualizadas. Debounce ≥ 250 ms en búsquedas. Medir en dispositivo real (Fase 7) antes de dar por cerrada una pantalla.

### 14. Copy
- Verbos claros y activos ("Cobrar", "Recibir mercancía", "Guardar borrador"). El mismo nombre para la acción en botón y confirmación. Errores: qué pasó y cómo corregirlo, sin disculpas ni vaguedad. Estados vacíos: una invitación a actuar, no un adorno.

### 15. Anti-patrones (no hacer)
Dashboard SaaS de tarjetas iguales, KPIs decorativos, hex sueltos, `window.confirm`, texto <14 px, targets <48 px, hover como única señal, iconos-carácter, doble navegación, cabeceras duplicadas, listas de miles de filas sin virtualizar, animaciones de entrada por sección, cambiar contratos API por motivos visuales.

### 16. Checklist antes de cerrar un cambio de UI
1. Se ve y opera bien a 1366×680 táctil, y se reorganiza en 1200 / 900 / 640.
2. Targets ≥ 48 px, foco visible, sin hover obligatorio.
3. Solo tokens (`var(--…)`), sin hex sueltos; módulo con color + icono + título + toldo.
4. Sin `window.confirm`; cifras con `money`; iconos de `lucide-react`.
5. `npm run typecheck` y `npm run build` pasan; tests backend sin cambios de contrato.
6. Venta ↔ Recepción no pierde estado.
